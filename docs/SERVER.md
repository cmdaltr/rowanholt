# Rowanholt as a team server

One Rowanholt on a central host, used by a DFIR team through their browsers or the desktop app's "connect to a server" mode. The evidence stays on the server's storage, the heavy tools (Volatility, Plaso, ClamAV, Ollama for Aulë) run on one well-specified box, and cases live in one place, with one audit trail.

A local install (an analyst's own machine, the lab) is unchanged. Everything here switches on with `rowanholt server init`.

## What changes on a server

| | Local | Server |
|---|---|---|
| Network | Every service's port published | Caddy only: 443 (and 80 for redirects and ACME); Splunk, Kibana and the Navigator on 7755, 5601 and 5602 through Caddy, behind the Rowanholt sign-in |
| TLS | None | Caddy: its own CA, Let's Encrypt, or your organisation's certificate |
| Sign-in | Optional; guest access; open sign-up | Required for every API route; no guests; admins create accounts; single sign-on (OIDC) optional |
| Jobs | Everyone sees everything | Each job is visible to its owner, the users it's shared with, and admins |
| Aulë | Every case | The cases behind jobs you can see |
| Admin areas | — | Lab, Andúril and Mordor downloads are admin-only |
| Frontend | Development server | Production build (nginx), same origin as the API |
| Secrets | Built-in defaults | Generated by `server init`; the stack refuses to start without them |

Server mode is the backend setting `ROWANHOLT_SERVER_MODE`, which `deploy/server/docker-compose.server.yml` sets. The checks live in one middleware (`src/web/backend/auth/access.py`), so a route added later is covered without remembering to protect it.

## Setting up

Requirements: a Linux host with Docker Engine and Compose 2.24 or later, and a DNS name for it. Ubuntu 24.04 with Docker's own packages is the tested shape; Rocky, RHEL and Alma 9 need the steps in [Rocky, RHEL and Alma](#rocky-rhel-and-alma) first, and Windows Server runs it in WSL 2 ([Windows Server](#windows-server)).

```bash
git clone https://github.com/cmdaltr/rowanholt.git && cd rowanholt
./rowanholt install
rowanholt server init rowanholt.dfir.example.org
rowanholt start
```

`server init` writes the server settings into `.env` (mode 600): the hostname, the certificate choice, a random `SECRET_KEY`, the first admin's password (printed once), and random Postgres, Elastic and Splunk passwords for stores that don't exist yet. Run it again to change the hostname or certificate; secrets already set are kept. From then on, `rowanholt start`, `stop` and `status` use the server profile without being asked (`--server` forces it).

With Splunk, Elastic and the Navigator:

```bash
COMPOSE_PROFILES=siem rowanholt start
```

Sign in at `https://rowanholt.dfir.example.org` as `admin` with the printed password, and change it under Account.

### Certificates

| `--tls` | Certificate | Clients |
|---|---|---|
| `internal` (default) | Caddy's own CA | Trust its root: `rowanholt server ca > rowanholt-root.crt`, then distribute it (MDM, Group Policy, `update-ca-certificates`) |
| `you@example.org` | Let's Encrypt | Nothing to do; the name must reach the host on 80 and 443 |
| `files` | `deploy/server/certs/rowanholt.crt` and `rowanholt.key` (your PKI) | Whatever already trusts your PKI |
| `tailscale` | Tailscale's (Let's Encrypt) for the server's MagicDNS name | Nothing to do on the tailnet |

On a tailnet, name the server by its MagicDNS name (`rowanholt.<tailnet>.ts.net`) and use `--tls tailscale`, with HTTPS certificates turned on for the tailnet (admin console, DNS). Caddy hands `*.ts.net` names to a Tailscale daemon its container can't reach, so `internal` or an email address there would serve no certificate at all; `server init` refuses them. The certificate lasts 90 days: `rowanholt server cert` renews it when it's due and restarts the proxy, and weekly from cron is enough (`17 4 * * 1 /path/to/rowanholt server cert`). Other apps on the same tailnet node serve the same certificate and need their own restart.

When something else on the host is the front door on 443, `--https-port <port>` (for example `8443`) serves Rowanholt there instead: the web app, API and Aulë's MCP server move to `https://<host>:<port>`, 80 is left free (the proxy's redirect listens on the host's loopback only), and Splunk, Kibana and the Navigator keep their ports. Running `server init` again keeps the port; `--https-port 443` goes back. MCP clients registered at the old URL need registering again at the new one.

### A name of its own on a tailnet

On a tailnet node that hosts other apps too, `--service <name>` gives Rowanholt its own address with no port, `https://<name>.<tailnet>.ts.net`, as a [Tailscale Service](https://tailscale.com/kb/1552/tailscale-services):

```bash
rowanholt server init homelab.tail180683.ts.net --tls tailscale --https-port 8443 --service rowanholt
rowanholt start
```

Tailscale terminates TLS for the name with a certificate of its own and hands each request to the proxy over plain HTTP on the host's loopback (`deploy/server/Caddyfile.service`, published on `127.0.0.1:5680`–`5683` by `docker-compose.service.yml`, which `rowanholt start` adds while `.env` sets `ROWANHOLT_SERVICE`). The name's 443 is the web app, API and Aulë's MCP server; its 7755, 5601 and 5602 are Splunk, Kibana and the Navigator. The name becomes `ROWANHOLT_PUBLIC_URL`; the host-and-port address keeps working (`ROWANHOLT_OTHER_URLS`, an allowed origin for the backend and Aulë's MCP server), and the node's certificate and `server cert` are unchanged.

Before the first `--service`, in the tailnet's admin console or through its API:

1. Tag the server (only a tagged device can host a Service), e.g. `tag:homelab`, with Tailscale 1.86 or later on it and on every client.
2. In the policy file, auto-approve the Service for that tag and let the people who use Rowanholt reach its ports:
   ```json
   "autoApprovers": { "services": { "svc:rowanholt": ["tag:homelab"] } },
   "grants": [ { "src": ["autogroup:member"], "dst": ["svc:rowanholt"], "ip": ["443", "7755", "5601", "5602"] } ]
   ```
3. If `server init` says Tailscale doesn't know the Service, define it once under Services with endpoints `tcp:443, tcp:7755, tcp:5601, tcp:5602`.

Afterwards register MCP clients again at the name, and for single sign-on add `https://<name>.<tailnet>.ts.net/api/auth/oidc/callback` as a redirect URI. Sign-in cookies belong to the address they were made at, so a browser signs in once at each address it uses; Splunk, Kibana and the Navigator send it to the sign-in page at the address it's on. `--service off` drops the name and puts the port address back as the public URL.

### Rocky, RHEL and Alma

These ship Podman, not Docker, and enforce SELinux. Rowanholt needs Docker Engine from Docker's own RHEL repository; Podman's Docker-compatible socket isn't supported (Andúril and the worker are untested on it), and `rowanholt start` stops with these steps if `docker` is missing or is Podman's:

```bash
sudo dnf remove -y podman-docker podman runc
sudo dnf install -y dnf-plugins-core
sudo dnf config-manager --add-repo https://download.docker.com/linux/rhel/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"    # then sign in again
```

**SELinux** stays enforcing. When `/sys/fs/selinux/enforce` is 1, `rowanholt start` adds `deploy/docker-compose.selinux.yml` (and, on a server, `deploy/server/docker-compose.selinux.yml`), which runs the services that mount host folders (the backend, frontend, proxy, Splunk, Kibana's set-up and Andúril) with `label=disable`. The alternative, relabelling each folder with `:z`, rewrites the `security.selinux` attribute of every file under it: across an evidence store that's slow, it fails on read-only and NFS mounts, and it changes the evidence's own metadata. Nothing on the host is relabelled. The worker is privileged already (it mounts images), so it was never confined. Named volumes (Postgres, Redis, Splunk's and Elastic's data) keep Docker's own labels.

**firewalld.** When it's running, `server init` opens the proxy's ports in the default zone and says which: 80 and 443 (or the `--https-port`), 7755, 5601 and 5602. Nothing else is published, so nothing else needs opening.

### Windows Server

Rowanholt's images are Linux containers, and Docker Desktop isn't supported or licensed on Windows Server, so on Windows Server 2022 or 2025 the server is a WSL 2 distribution of its own running Docker Engine. `scripts/server/windows/Install-RowanholtServer.ps1` sets it all up, from an administrator PowerShell on the server:

```powershell
git clone https://github.com/cmdaltr/rowanholt.git; cd rowanholt
.\scripts\server\windows\Install-RowanholtServer.ps1 -Hostname rowanholt.dfir.example.org `
    -CertificateThumbprint 3F2A... -EvidencePath D:\Evidence -WslPath E:\Rowanholt\wsl
```

It turns WSL 2 on (the first run may stop and ask for a reboot: run it again afterwards), imports Ubuntu 24.04's WSL image (SHA-256 checked) as a distribution named `Rowanholt` with its disk under `-WslPath`, installs Docker Engine from Docker's repository under systemd, clones Rowanholt into `/opt/rowanholt` inside it, and runs the same `rowanholt server init` as on Linux. The first admin's password is printed then, as on Linux.

| Parameter | |
|---|---|
| `-CertificateThumbprint` | A certificate in `Cert:\LocalMachine\My` with an exportable key, exported once with a throwaway password, converted to `deploy/server/certs` inside WSL and the export deleted: `--tls files`. Without it, `-Tls internal` (the default) or an email address for Let's Encrypt |
| `-EvidencePath` | Folders on Windows volumes, mounted as on Linux (`D:\Evidence` is `/mnt/d/Evidence`, read-only in the backend) and added to `ROWANHOLT_EVIDENCE_PATHS` |
| `-WslPath` | Where the distribution's virtual disk goes. Cases are written inside it, so put it on a data drive |
| `-HttpsPort` | As `--https-port` |
| `-Credential` | The account the boot task runs as: the one running the script, since a WSL distribution belongs to a user; its password is asked for so the task runs with nobody signed in |

**Reaching it.** WSL 2 sits behind its own NAT with a new address each boot. The `Rowanholt` scheduled task (at startup, as that account) runs `rowanholt start` inside WSL, points `netsh interface portproxy` at the distribution's current address for the proxy's ports (80 and 443, or the `-HttpsPort`, then 7755, 5601 and 5602), and stays attached so WSL doesn't stop the distribution. A Windows Firewall rule (group `Rowanholt`) opens the same ports. `localhostForwarding=false` in the account's `.wslconfig` keeps WSL's own loopback relay off those ports. Its log is `%ProgramData%\Rowanholt\start.log`; portproxy needs the IP Helper service, which runs by default.

**Evidence on Windows volumes** goes through WSL's file sharing, which is far slower than its own disk: for large images, copy them into the distribution first (`\\wsl$\Rowanholt\srv\evidence` from Windows, mounted like any Linux folder). WSL 2 takes half the server's memory by default; set `memory=` under `[wsl2]` in the account's `.wslconfig` for more.

Inside, it's a Linux server: `wsl -d Rowanholt -u root -- /opt/rowanholt/rowanholt <command>` (`status`, `server users`, `stop`), and a `git pull` there updates it. Run the script again to change the hostname, certificate or evidence folders.

### Evidence

Paths in Rowanholt are paths on the server. Mount your evidence storage on the host and make it visible to the containers with a `docker-compose.local.yml` beside `docker-compose.yml` (the launcher adds it when it exists; it's gitignored):

```yaml
services:
  backend:
    volumes:
      - type: bind
        source: /srv/evidence
        target: /srv/evidence
        read_only: true
  celery-worker:
    volumes:
      - type: bind
        source: /srv/evidence
        target: /srv/evidence
```

Then tell Rowanholt it may use it, in `.env`:

```bash
ROWANHOLT_EVIDENCE_PATHS=/srv/evidence
```

Several are separated by commas. Without it, only `/mnt`, `/media` and `/tmp/rowanholt` are accepted. Gandalf archives copied to the share are picked up like any other source.

## Users

```bash
rowanholt server users list
rowanholt server users add alice alice@example.org            # prompts for a password
rowanholt server users add bob bob@example.org --admin
rowanholt server users role alice admin
rowanholt server users disable bob
rowanholt server users password admin                          # a locked-out admin
```

These work inside the backend container, so they work when nobody can sign in. Admins can do the same through the API (`/api/auth/users`). Passwords on a server need at least 12 characters, and repeated failures lock the username (`max_login_attempts`, `lockout_duration_minutes`; see below).

### Single sign-on

Register Rowanholt with your identity provider as a confidential web application:

| Setting | Value |
|---|---|
| Redirect URI | `https://<hostname>/api/auth/oidc/callback` |
| Grant | Authorization code (Rowanholt uses PKCE) |
| Scopes | `openid profile email` |
| Claims | A groups claim, if roles should follow groups |

Then add to `.env` and restart:

```bash
OIDC_ISSUER=https://login.microsoftonline.com/<tenant-id>/v2.0
OIDC_CLIENT_ID=...
OIDC_CLIENT_SECRET=...
OIDC_DISPLAY_NAME=Microsoft          # the button says "Sign in with Microsoft"
OIDC_ADMIN_GROUP=<group id or name>  # members become Rowanholt admins; others are users
OIDC_ALLOWED_GROUP=<group>           # optional: only members (and admins) may sign in
ROWANHOLT_LOCAL_LOGIN=false          # optional: SSO only; admins keep a password as break-glass
```

The ID token is verified against the issuer's published keys, its audience and the sign-in's nonce. Users are matched on issuer and subject, so a renamed account stays the same Rowanholt user; the first sign-in creates them. With `OIDC_ADMIN_GROUP` set, the role follows the group at every sign-in. Entra ID puts group object IDs in the `groups` claim (enable it under Token configuration); Okta and Keycloak need a groups claim mapper.

## Sharing jobs

A job belongs to the user who created it. On its page, the Access panel shows the owner and who it's shared with; the owner or an admin adds and removes people. The people it's shared with can see and work on it (cancel, restart into its output with `fresh=false`, export, ask Aulë), but can't reshare it, delete or archive it, or restart it with fresh output: those lose the owner's work, so they're the owner's or an admin's. Jobs created before the server existed have no owner: admins see them and can share them.

Everyone who can see a job can work the case together from **Browse Case** on its page. They can flag rows as findings, confirm or dismiss them, assign hosts, keep notes, and follow the activity feed. All of that lives in Postgres and points at rows of the case's output; it never changes the case directory.

Case numbers name output directories, so they're unique across the server: creating a job with a case number someone else used is reported as a clash, without showing their job.

## The desktop app

People can use the server from the desktop app instead of a browser tab: in setup, choose **Connect to my team's Rowanholt server** and enter the hostname. Nothing runs locally: no Docker, no files. The Mac app needs the server's certificate to be trusted by the Mac (Keychain); the Linux and Windows apps open it in an Edge or Chromium app window. See `app/README.md`.

## Limits worth knowing

- **Andúril holds the Docker socket.** It's opt-in (`rowanholt anduril enable`) and admin-only on a server, but whoever administers it administers the host's Docker.
- **Splunk and Kibana** have their own users and indexes. Rowanholt's sign-in in front of them keeps out anyone without a Rowanholt account, but doesn't map job sharing onto their data. The Navigator does follow it: a case's layer is served only to people who can see the case, and layers from command-line runs (no job) only to admins.
- **Sessions are 24-hour tokens** (`access_token_expire_minutes`); disabling a user stops their next request, since every request checks the user store.
- **Accounts live in the checkout, not the database.** The user store is `src/web/backend/data/users.json`, on the host through the backend's bind mount and kept out of the images by `.dockerignore`, so a rebuild or a pull leaves accounts alone. It's gitignored, so `git clean -x` deletes it: `rowanholt server backup` (below) keeps it with `.env` and the database.

## Backups

```bash
rowanholt server backup /backups/rowanholt            # --keep 14 by default
```

Each run writes a dated folder holding the database dump (jobs, findings, notes, activity, API tokens, threat intelligence), `users.json`, `.env` and `docker-compose.local.yml`. The dump is read back before the backup counts, and a failed run leaves nothing behind. The folder holds the server's secrets, so it's created owner-only: keep it off shared storage. Case output and evidence aren't in it; back up the evidence storage on its own. Daily from cron, to storage that isn't the server's own disk:

```
30 3 * * * /path/to/rowanholt server backup /backups/rowanholt >/dev/null
```

To restore on a fresh checkout: put `.env`, `users.json` (in `src/web/backend/data/`) and `docker-compose.local.yml` back, `rowanholt start`, then load the dump and restart the backend:

```bash
docker exec -i rowanholt-postgres pg_restore -U rowanholt -d rowanholt --clean --if-exists --no-owner < rowanholt.pgdump
docker restart rowanholt-backend
```

## How sign-in lockouts work

Failed password sign-ins are counted in Redis, so restarts don't reset them. Five failures from one address lock that username for 15 minutes from that address only: someone guessing at a colleague's account locks themselves out, not the colleague. Fifty failures across all addresses lock the username everywhere, to catch guessing spread over many machines. If Redis is down, the counts are held in the backend process until it's back.

## The schema

The backend migrates its database on start with Alembic (`src/web/backend/alembic/`), under a Postgres advisory lock so the backend and the worker starting together don't race. A database from before migrations is recognised and stamped, not recreated. A worker image built before Alembic was added keeps creating any missing tables itself, as it always did.
